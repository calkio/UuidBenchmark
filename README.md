# UuidBenchmark

Сравнение способов генерации UUID (v4 baseline и четыре реализации v7) по
двум измерениям: чистая скорость генерации и поведение PostgreSQL-индекса
при вставке большого объёма строк.

## Состав

- **UuidBenchmark.Generation** — BenchmarkDotNet-проект, чистая скорость
  генерации без похода в БД (CPU/allocation overhead).
- **UuidBenchmark.Database** — EF Core модели, 5 таблиц (по одной на
  стратегию, чтобы не смешивать фрагментацию), конфигурация во Fluent API.
- **UuidBenchmark.Cli** — консольный раннер: batch-insert с чекпоинтами по
  времени + финальный отчёт по фрагментации через `pgstattuple`/`pgstatindex`.
- **docker-compose.yml** — PostgreSQL 16 (uuidv7() нативно появилась только
  в PG 18, поэтому используем SQL-функцию `uuid_generate_v7()` из
  `db-init/`).

## Требования

- .NET 9 SDK (нужен ради `Guid.CreateVersion7()`)
- Docker / Docker Compose

## Запуск

```bash
docker compose up -d

dotnet restore

# Микробенчмарк генерации (обязательно Release)
dotnet run --project src/UuidBenchmark.Generation -c Release

# Интеграционный тест: вставка + отчёт по фрагментации
dotnet run --project src/UuidBenchmark.Cli -- \
  --strategy all \
  --total-rows 1000000 \
  --batch-size 1000
```

Полный список опций CLI: `dotnet run --project src/UuidBenchmark.Cli -- --help`

Строка подключения по умолчанию рассчитана на локальный docker-compose;
переопределить можно через `--connection-string` или переменную окружения
`UUID_BENCHMARK_CONNECTION_STRING`.

## Как читать отчёт по фрагментации

- **avg_leaf_density** — насколько плотно заполнены страницы индекса.
  У здорового b-tree (fillfactor по умолчанию) — ориентировочно ~90%.
  Заметно ниже — значит, много "воздуха" от page split'ов.
- **leaf_fragmentation** — процент листовых страниц индекса, физически
  лежащих на диске не по порядку. Это прямое проявление случайных вставок
  v4: чем выше, тем сильнее произвольный I/O при обходе индекса.
- **dead tuple %** — доля "мёртвых" строк (актуально больше для
  update/delete нагрузки, но тоже влияет на объём чтения).

Для v4 обе метрики должны заметно деградировать с ростом объёма данных,
для всех вариантов v7 — оставаться стабильно близкими к "здоровому"
состоянию, независимо от объёма.

## Важный нюанс при интерпретации `v7dbside`

В отличие от четырёх code-side стратегий, `rows_v7_dbside` использует
`DEFAULT uuid_generate_v7()` на стороне БД, а не клиентский
`ValueGenerator`. Из-за этого EF Core не может собрать один
`INSERT ... VALUES (...), (...), (...)` на весь батч — ему нужно вычитать
сгенерированное значение через `RETURNING` для каждой строки, поэтому
батч превращается в несколько отдельных `INSERT`-команд, отправленных
одним round-trip'ом (implicit batching в Npgsql), а не в один
multi-values `INSERT`.

Это значит, что если `v7dbside` окажется медленнее остальных v7-вариантов
по вставке — разница может объясняться этим протокольным нюансом, а не
самой генерацией UUID. Полезно смотреть отдельно на `avg_leaf_density` /
`leaf_fragmentation` (тут `v7dbside` должен вести себя так же хорошо, как и
остальные v7) и отдельно на throughput вставки (тут сравнение не совсем
честное между DB-side и code-side генерацией).

## Что можно добавить дальше

- Параллельные вставки в несколько потоков/подключений одновременно —
  именно в этом сценарии разница между v4 и v7 максимально заметна
  на реальных нагрузках (см. обсуждение "random page miss under
  concurrent writers" в статьях про UUID-индексы).
- Замер скорости выборки диапазона по времени после загрузки (`SELECT`
  по `CreatedAtUtc BETWEEN ...`) — покажет разницу не только во вставке,
  но и в клиентском чтении.
- `REINDEX` / `pg_repack` после загрузки — сравнить, насколько сильно
  каждая стратегия восстанавливается после принудительной дефрагментации.
